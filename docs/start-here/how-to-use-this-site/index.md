# How to Use This Site: Paths, Pages, Downloads and Help

This site teaches the work of an SDET (a tester who writes code) through real tasks: "test this API", "check the order was saved", "set up BDD for the team". Every page shows exactly what to type and what you should see. Every topic comes with files you can download and use at work. This page shows how it all fits together, so you never wonder where to go next.

!!! note "Before you start"
    Nothing. Read this page first, then [set up your computer](../environment-setup/index.md).

## What you will learn

- Where to start: a learning path, or the task you have today
- How a topic page and a lesson are built, so you know where to look
- What each kind of box on a page means
- How to download a topic's files and run them
- How to track your progress, and where to ask for help

## Why this matters at work

At work nobody hands you a course. You get a task, a deadline and a codebase you've never seen. The topic pages here are written the same way: they start from a manager's request and walk through how an experienced tester thinks it through, step by step. Learning this way also teaches you how to learn a new area fast, which you'll do for your whole career.

## The idea in plain words

!!! info "In plain words"
    The site is like a driving school with a good map. A learning path is the route from your first lesson to the motorway. The topic pages are the stops on the way. At each stop, someone sits next to you and says exactly what to do, and what you should see when you've done it.

## Step by step

### 1. Pick where to start

Pick the one that fits you today:

| If you... | Start with |
| --- | --- |
| Have never written code | The [Manual tester to automation](../../learning-path.md#manual-tester-to-automation) path |
| Can write some Python and want to build a test suite | The [Build a whole test suite](../../learning-path.md#build-a-whole-test-suite) path |
| Already automate tests and plan testing for a team | The [Design how a team tests](../../learning-path.md#design-how-a-team-tests) path |
| Have an interview coming up | The [Interview prep in 4 weeks](../../learning-path.md#interview-prep-in-4-weeks) path |
| Have a task at work right now | The "I need to…" list on the [home page](../../index.md), then that topic |
| Aren't sure what you know | The [Skills Matrix](../skills-matrix.md): tick what you can do; the first empty box is your next lesson |

You don't have to go in order. Every page has a **Before you start** box that says what to read first.

### 2. Read a topic page

A **topic** is one area of the work, like [API testing](../../core-automation/api-testing/index.md). Its first page walks through one real task, always in the same order:

1. **In plain words** and **Your task**: the idea in one everyday sentence, and the request from your manager.
2. **Before you start**: what to read or install first.
3. **Jump to what you need**: the topic's lessons, each one skill.
4. **Nine sections**, the way an experienced tester handles any new task: understand the ask, picture the system (a diagram), learn just enough, get something running, decide what to put in, write a one-page plan, build in small steps, check it with your team, and keep learning.
5. **How an experienced SDET thinks about this**, **Red flags** and **Stuck? Try this**: the habits, the warning signs, and the first things to try when it doesn't work.
6. **Templates**: the files to use at work, ready to copy, with a link to the whole folder on GitHub.
7. **Official resources**: where to read more.

### 3. Read a lesson

A **lesson** teaches one skill, like [writing step definitions](../../core-automation/bdd-testing/step-definitions.md). Lessons always have the same parts, so you can find what you need quickly:

| Part | What it gives you |
| --- | --- |
| Before you start | What to read or install first |
| What you will learn | The skills, in a short list |
| Why this matters at work | Where you'll use it |
| The idea in plain words | The idea, with an everyday example |
| Step by step | What to type, and what you should see after each step |
| When it goes wrong | Real errors, and what each one means |
| Common mistakes | What people often get wrong, and one error explained in full |
| Try it yourself | An exercise, with the answer folded away |
| Quick check | Two or three questions to test yourself |
| References | The official documentation |

When you finish a lesson, click **Mark this lesson as done** at the end.

### 4. Know the boxes

| Box | Means |
| --- | --- |
| **Before you start** | Read or install this first |
| **In plain words** | The idea, with no technical words |
| **Your task** | The request you're working on, as a manager would say it |
| **Check: you should now be able to** | Stop and check you can do this before moving on |
| **Common mistakes** | Don't do these |
| **If you see this error** | One error, word for word, and the fix |
| **Solution** or **Answer**, folded | Click it to open. Try first, then look |

Code is in two kinds of boxes. The first is what you type. The box under it, with plain text, is what you should see. Tabs (like **macOS and Linux** and **Windows**, or **behave** and **pytest-bdd**) show the same step in different ways: pick yours.

Every output on this site comes from a real run. Yours will match, except:

- **Times.** `in 0.48s` may be `in 0.61s` on your computer.
- **Paths.** `...` stands for the start of a long folder path, which is different on every computer.
- **Versions.** The last line of each page says which versions it was written for. Use those, and what you see will match.

### 5. Copy the files and run them

Each topic's **Templates** section has every file in its own tab, with a **copy** button. The whole folder is also on GitHub. Each file starts with a line saying where it came from: keep it. The code is free to use at work, under the [MIT license](../../about.md#free-to-use-with-credit).

[Environment setup](../environment-setup/index.md) shows how to install Python and Docker, then run a topic's files, step by step.

### 6. Track your progress

- **Mark this lesson as done** at the end of a lesson.
- Tick what you can do in the [Skills Matrix](../skills-matrix.md).

Both are saved only in your own browser, on this computer. Nothing is sent anywhere, and you don't need an account.

### 7. Look up words, search, get help

- **A word you don't know?** The [Glossary](../../glossary.md) explains every testing word in plain English. Short forms like API and BDD have a dotted underline: point at one (or tap it on a phone) to see what it means.
- **Looking for something?** Use the search box at the top of every page, or browse pages by [tag](../../tags.md).
- **Stuck?** First the page's **When it goes wrong** section, then the topic's **Stuck? Try this** box.
- **Something on a page is wrong or unclear?** Answer **No** under "Was this page helpful?" at the end of the page, and tell us what was unclear. Or use the "Edit this page" button at the top of the page.

!!! success "Check: you should now be able to"
    Pick where to start, find the step-by-step part and the "When it goes wrong" part of any lesson, download a topic's files, and say where your progress is saved.

## When it goes wrong

- **Your output doesn't match the box.** Check the versions in the last line of the page against yours (`python --version`, `python -m pip list`). Then check you're in the right folder, with the virtual environment on. Different times and paths are fine.
- **A page says "Coming soon".** That topic is still being written. The [Learning Path](../../learning-path.md) shows what's ready, and the [Changelog](../../changelog.md) shows what's new.
- **Your ticks and "done" marks are gone.** They're saved in the browser, so a private window, another browser, or clearing the site's data starts again from empty.
- **A command fails before the tests even start.** It's almost always the setup. Go back to [Environment setup](../environment-setup/index.md#when-it-goes-wrong).

## Common mistakes

!!! warning "Common mistakes"
    - **Reading without running.** You learn by typing the commands and seeing the result yourself. Run every step.
    - **Opening the solution first.** Try for ten minutes. Getting stuck, then finding the way out, is the real lesson.
    - **Skipping "Before you start".** Most confusion comes from a missing earlier step.
    - **Trying to learn everything before starting.** Pick one task and finish it. Then the next.

!!! failure "If you see this error"
    **`ModuleNotFoundError: No module named 'pytest'`**, in the first lesson you try.
    The virtual environment isn't on, or it was never made. Do steps 6 and 7 of [Environment setup](../environment-setup/index.md#7-run-your-first-tests), then try again.

## Try it yourself

Find the lesson that explains what to do when pytest-bdd says `Step definition is not found`. Use the search, not the menu.

??? success "Solution"
    Search for `Step definition is not found`. It's in [Step definitions](../../core-automation/bdd-testing/step-definitions.md#when-it-goes-wrong), under "When it goes wrong": a step's text doesn't match any pattern, often because of a typo.

## Quick check

1. Where do you find the files for a topic?

    ??? question "Answer"
        In the topic's **Templates** section, each in a tab with a copy button. The whole folder is on GitHub too.

2. Your test run says `in 0.61s` and the page says `in 0.48s`. Is something wrong?

    ??? question "Answer"
        No. Times differ between computers. Compare the results: passed, failed, skipped.

3. Where is your progress saved?

    ??? question "Answer"
        Only in your own browser, on this computer.
