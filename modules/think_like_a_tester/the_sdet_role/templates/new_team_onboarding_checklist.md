## Access (week 1)

- [ ] I can clone the app repository and the test repository
- [ ] I can open a pull request, and I know who reviews test code
- [ ] I know the test environments and their URLs (dev, staging, others): <list>
- [ ] I have test accounts for each environment. Passwords live in: <secret manager or vault, never in chat>
- [ ] I can see CI pipeline runs and their logs: <link>
- [ ] I can open the bug tracker and the test management tool: <links>
- [ ] I can read the app's logs and monitoring dashboards: <links>
- [ ] I am in the team chat, the release channel and the incident channel

## People (week 1)

- [ ] Who decides what a feature should do (product owner): <name>
- [ ] Who leads the developers: <name>
- [ ] Who fixes broken test environments: <name or team>
- [ ] When the team meets (stand-up, planning, review): <times>

## The product (weeks 1 and 2)

- [ ] I have used the main user journeys myself, by hand: <list them>
- [ ] I know which features bring in money or carry the most risk: <list>
- [ ] I have read the last five serious bugs or incidents, and what caused them
- [ ] I know how a change goes from a pull request to production, and how often the team releases

## The existing tests (week 2)

- [ ] I know where the tests live: <folders>
- [ ] I can run them on my computer. The exact commands: <commands>
- [ ] I know how long the full run takes: <minutes>
- [ ] I know which tests fail at random (flaky): <list>
- [ ] I know what is not tested yet: <list>
- [ ] I know who looks at failed test runs, and how fast

## My first useful change (weeks 2 and 3)

- [ ] Run the whole test suite and write down every problem I hit
- [ ] Make one small, useful change: fix a flaky test, add a missing smoke test, or fix the setup notes
- [ ] Open a pull request and get it reviewed and merged
